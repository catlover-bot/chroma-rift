## 調査で分かったこと

同じ「部屋の描画を確認できませんでした。」はrenderer生成、scene生成／mount、simulation、scene frame、主描画、native提示、shader／GL、および起動期限切れの複数箇所から発生する。文言と録画だけでは失敗段階を特定できない。`FirstPersonCanvas` の起動タイマーはready後に失敗へ変えない条件を持ち、単純な古いタイマー残存を示す証拠はなかった。R3F native 9.7.0 のCanvas wrapperは `state.gl.render` の主描画後に `endFrameEXP()` を一回呼ぶ。本実装の反射描画はwrapperではなく同じrendererのraw drawを使い、simulationを追加更新しない。

確定した別の欠陥は、鏡の背面または面の近くで反射を見送っても、前の反射テクスチャを使うshaderを本画面に残していたこと。エリア04の実StageSceneと現行 `planarMirror.ts` を同じSoftware WebGL rendererで描いた比較では、正面の反射の後に背面へ移ると、旧経路は更新していない像を表示した。今回、反射が成立しないフレームは不透明な背面材を選び、鏡面に近すぎる投影を避ける。鏡を本編から削除していない。この欠陥が実機の08:26の例外を起こしたとはまだ証明できない。

反射targetは384×384、samples 0、depthあり、stencilなし、mipmapなし、Threeの標準RGBA/unsigned-byteである。初回offscreen drawで実target構成とFBO statusを記録し、不完全なら主画面提示より前に理由付きで失敗させる。FBO status取得は初回だけとし、毎フレーム同期読み取りを増やさない。SwiftShaderでは同一scene/rendererで「主描画のみ」「target確保のみ」「反射あり」がいずれもGL error 0、target FBOは `0x8cd5` (complete)。iPhone EXGLが同じ結果かは未確認。

## 修正と復旧

`FIRST_FAILURE` に最初の段階、reason code、例外・stack、直前の成功した主描画／native提示／反射のframe番号、経過時間、renderer owner数、targetとGL状態、poseと進行revision、再試行回数を記録する。後のcleanupやtimeoutは最初の記録を上書きしない。内部previewのエラー画面から「詳細を表示」→「診断情報をコピー」を明示操作で選べる。診断は有界で、URL、メール、ユーザー・端末パス、トークン、UUIDを伏せ、自動送信しない。native build番号とchannelを取得する仕組みがないため `unknown` と表示する。

後続の監査で、描画失敗時には未提示フレームのruntimeを巻き戻した後に画面がposeを読んでいたため、診断の座標が実際に失敗したカメラ位置と異なる場合があると分かった。今は巻き戻し前のposeとrevisionを最初の失敗用に固定し、`poseSource=failed-unpresented-frame` と示す。checkpointには入れず、保存する進行と復帰位置の巻き戻しを維持する。巻き戻し後しか観測できない起動timeout等は `poseSource=current-controller` と区別する。R3F境界で未提示フレームの移動を強制し、診断のposeは移動後、保存側runtimeは移動前へ戻ることを検査した。

追加の監査で、Canvas単位の最初の記録は保持されても、明示retryが新しい画面sessionを作ると前の記録を失うことが分かった。最初の診断を画面ownerへ一つだけ保持し、連続して失敗する2回のretry後も同じ原文を表示・コピーする。retryで本編の主画面が実際にreadyとなったら故障の一連を終え、次の独立した失敗には新しい最初の記録を使う。開発用の箱描画確認だけが成功しても本編の最初の記録は消さない。これらを画面テストで区別した。

既存の失敗停止・最大2回の明示retry・Canvas退役・campaign保存を保った。新しいApp経路テストでは、03から04へ移った後、実controllerで隔離キーを取得して保存し、描画失敗3回、retry2回、上限表示、ホーム、アプリ冷再入場を通した。保存済みの鍵と未完了練習状態が維持され、mock Canvasの同時owner最大数は1。これは実iPhoneのcontext破棄や表示成功の証拠ではない。

native R3F境界の追加テストでは、鏡を含む主画面が一度ready／提示された後、次の反射raw drawで例外を注入した。`FIRST_FAILURE` は失敗前段階 `ready`、2番目のframe、最後に成功した主描画・反射・提示はいずれも1番目と記録した。失敗したframeに `endFrameEXP` を追加せず、targetと鏡の可視性を元に戻し、後続frameや古いcallbackで二重通知しない。GPUはmockであり、iPhoneの同じ失敗理由を確定する試験ではない。

同じnative R3F境界で正面→背面→正面の3フレームも検査した。反射pass数は1→1→2、背面の材は不透明な背面材、正面へ戻った材は再び反射shaderで、native提示は各フレーム一回。これは旧像を残さない修正が実StageSceneにも届くことのmock境界証拠であり、端末GPUでの描画証拠ではない。

さらにnative wrapperの失敗伝播を監査すると、shader callbackや主描画後のGL検査で失敗を記録しても、renderer delegateが通常returnするためR3Fの`endFrameEXP()`が同じ失敗フレームを提示し得た。修正前のnative境界テストで2経路とも提示1回を再現し、修正後は失敗フレーム提示0回、元のreason codeと例外保持を確認した。一度readyとなった後の次フレームGL失敗も同じ結果。これは失敗処理の確定欠陥だが、ユーザー録画の08:26で実際にshader/GL検査が起きた証拠はなく、その原因と同一視しない。

鍵取得後の案内を状態別にし、練習場所へ向かう控えめな壁印とレバー印を追加した。取得距離、必要操作、解法、敵、エリア番号、保存schemaは変えていない。
